# v0.2.6 — 합성 예정 슬롯 상태 변경과 감사 이력

작성: 2026-10-10 · 간호처방 시스템 단독 개발 · **실제 간호처방/EMR 상태·권한을 구현한 것이 아님**

## 범위 결정

v0.2.5 이후 임상 가치 재평가 및 연구 파일럿 산출물(`design/CLINICAL-VALUE-REASSESSMENT-v0.2.5.md`, `research/USABILITY-PILOT-v0.1.md`)을 보존한다. 병원의 실제 절차 확인 전 **개별 예정 슬롯**에서만 교육용 보류·재개·취소·연기를 모의한다. 처방 전체의 `draft/confirmed/held/cancelled` 상태전이 및 공식 기록 정정은 **실행하지 않음**. 이 상태 변경 역시 승인된 임상 업무 규칙이 아니다.

## 데이터 구조 (기존 schema 2 / 키 유지)

- `order.schedule.slots[n].id`와 최초 `at`는 변경하지 않음.
- 연기한 슬롯에만 선택적 `rescheduledAt`(ISO UTC)을 부여. 화면은 최초 시각과 현재 유효 예정 시각을 별도로 표시한다. 반복 처방의 타 슬롯은 변경하지 않으며 원래 `everyHours`는 최초 슬롯 간격만 의미한다.
- 변경할 때마다 **기존 `state.audit` 배열에 이벤트를 추가**, 별도 쓰기 저장소·데이터 변환 없음.

| 이벤트 | 허용 이전 상태 | 결과 | 이력 내용 |
|---|---|---|---|
| `slot_held` | `planned` | `held` | ID·이전/새 상태·사유·가상 변경자·시각 |
| `slot_resumed` | `held` | `planned` | 위와 동일 |
| `slot_cancelled` | `planned` 또는 `held` | `cancelled` | 위와 동일, 이번 구현에서 취소는 최종 상태 |
| `slot_postponed` | `planned` 또는 `held` | 상태 유지 | 직전 유효 시각 `oldAt`, 새로운 `newAt`, 사유·변경자·시각 |

- 변경 사유 2~200자 및 현재 로그인된 데모 간호사 계정의 PIN 재인증이 필요함. 이는 **동일 사용자 재인증 시뮬레이션**이며 기관 인증, 2인 확인, 실제 전자서명을 뜻하지 않음.
- 다른 개별 처방/환자에 속한 슬롯, 초안/기타 비확정 처방의 슬롯, 이미 실제 모의 수행 사건이 연결된 슬롯은 변경 거부.
- `cancelled`는 이 데모에서 재개·연기 불가; 이미 저장된 모의 수행/기록/링크는 삭제·이동하지 않음.
- 연기는 반드시 해당 슬롯의 현재 유효 시각보다 **나중 시각**만 받음. 실무상 '연기'만 모의하므로 앞당기기, 다른 슬롯 자동 일정 재계산, 날짜별 근무조 로직은 구현하지 않음.
- 과거 스키마 2 저장값은 `slotId`, `rescheduledAt` 또는 새 감사 액션이 없어도 그대로 유효. 기존 데이터 자동 변경·초기화 없음.

## UI와 집계

- 기존 현황 카드에 원래 슬롯 수(취소 포함)와 진행 가능/보류/취소 슬롯 수를 구분. **계획 수치만으로 완료/누락을 판정하지 않음.**
- 각 예정 행에서 가능한 상태 변경만 표시. 새 대화상자에 이유/필요 시 변경 예정 시간/데모 PIN 입력. 처리 후 원래 시각·바뀐 시각·수행·기록 상태를 조회.
- 처방별 상세 이력에 슬롯 ID·액션·사유·작성자·시각·시각 변경 내역 표시; 원본 처방 ID와 연결된 개별 기록 그대로 유지.
- Kardex식 간호처방지에는 별도 예정 요약만 읽기 전용으로 표시. 그룹화는 화면 전용이고 원본 주문을 병합하지 않는다.

## 위험 및 남은 의사결정

- 이번 모델은 정확한 병원 간호처방·수행 권한이나 정정 절차를 알 수 없어 **실사용 불가**.
- 상태 이력은 localStorage 내의 교육용 이벤트이며 암호학적 불변 감사추적/법적 서명이 아님. 로컬 저장소 편집·삭제는 막을 수 없다.
- 병원 단위에서 보류/취소의 의미, 취소 후 회복 여부, 이미 수행된 행위와 계획 변경의 관계, 근무조별 시간창, 현재 시각 기준 제약, 정정 권한 등은 검증·사용자 결정 필요.
- 다음은 임상적 가치 재검토 문서의 Gate 0(기존 기능/현장 문제 확인)을 우선. 그 전까지 더 큰 상태/임상 규칙 확장과 서버/PRN/MICU 통합은 보류.
