# v0.2.5 — 반복 간호처방 예정·수행·기록 구분

작성: 2026-10-10 · **간호처방 프로젝트 단독 / 합성 데이터 교육·UI 기술검증용** · 실제 병원 규칙 및 임상 적합성 미검증

## 핵심 데이터 계약

기존 `schema: 2` / localStorage `nursing-order-demo-v02` / 기존 주문·수행·기록·링크·감사 이력 **그대로 보존**. 저장 데이터의 일괄 마이그레이션이나 초기화 없음.

```js
// 새 처방에만 존재할 수 있는 선택적 필드
order.schedule = {
  kind: 'interval',       // once | interval | conditional
  everyHours: 8,          // interval 전용, 합성 예시
  slots: [
    {id: order.id + '-S001', at: '2026-10-11T01:00:00.000Z', status: 'planned'},
    {id: order.id + '-S002', at: '2026-10-11T09:00:00.000Z', status: 'planned'},
    {id: order.id + '-S003', at: '2026-10-11T17:00:00.000Z', status: 'planned'}
  ]
};
// 조건부: {kind:'conditional', condition:'합성 조건', slots:[]}
// 모의 수행에만 선택적으로 연결되는 예정 식별자
execution.slotId = order.id + '-S001';
```

- `order` 1개는 **개별 처방 1건**이다. `slots`는 그 처방의 **예정 시점** 목록이며 처방 수가 아니다.
- `executions`는 별도 고유 ID를 가진 **실제 시뮬레이션 수행 사건**이다. `slotId`는 사용자가 특정 예정 시점의 버튼을 선택한 경우에만 붙는다. 동일 슬롯에 여러 사건이 있을 수 있다.
- `records`는 독립된 **간호기록 사건**으로 기존 `links`를 통해 수행에 연결되며 1:1이라고 단정하지 않는다.
- 기존 `details.frequency`는 정성적 설명(예: 매 근무조)이며 일정 생성에 사용하지 않는다.
- 기존/조건부 처방의 계획 횟수는 `null`(미정)으로 표시한다. `0회` 계획으로 변환하거나 과거 수행 시각을 자동 매칭하지 않는다.
- 화면에서 합산할 때 알려진 예정 시점의 총수와 **예정 미정 처방 건수**를 나란히 제시한다. 특히 그룹별 예정 합계를 전체 처방의 확정된 총횟수처럼 표기하지 않는다.
- `slot.status`는 예정·보류·취소(`planned/held/cancelled`) 조회와 저장검증의 표현만 준비했다. **이번 버전에는 상태 변경 및 정정 UI·이력 생성 기능을 추가하지 않았다.** 처방 자체의 `draft/confirmed/held/cancelled` 상태와 별개.
- `at`은 ISO UTC, 입력은 **브라우저 현지 시간**으로 해석해 변환. 일광절약시간 및 병원·근무조별 타임존 정책은 검증하지 않음.

## UI 작동

1. 간호활동(ACT) 검색 → 기존 부위/목적/빈도/방법/제품 선택은 그대로 둔다.
2. 새 `예정 시점 · 반복 조건`에서 **미지정(default)** / **일회성** / **주기 반복** / **조건부** 중 하나를 선택한다. 주기는 첫 시각과 **1~48시간 간격, 2~24회**를 입력한다. 모든 숫자와 시간은 합성 사례용일 뿐 임상 권고값이 아님.
3. 임시저장 → 기존 계정 PIN 재인증 → 확정 흐름과 상태 검증을 변경하지 않는다.
4. 현황 화면에서 **개별 처방/확정/임시저장/예정/예정 미정/수행/기록**을 각각 집계. 각 처방의 슬롯 ID·예정 시각·예정 상태·연결 수행/기록 수를 표시한다.
5. 확정 처방에서는 기존 **일반 모의 수행 추가**(예정 미연결)를 유지하고, 해당 슬롯에 **이 예정에 모의 수행 연결** 버튼을 추가한다. 사건 기록자는 기존 로그인 사용자. 기록 작성은 이전과 동일하게 개별 수행 사건에 연결한다.
6. 같은 가상 코드 그룹은 조회 편의용 요약일 뿐 원본 개별 처방·다른 상세 조건·예정·사건·기록을 병합하지 않는다. Kardex 처방지에도 '예정 3회/조건부 미정/미지정' 정도의 설명만 표시한다.
7. 환자 변경 시 예정 입력폼을 초기화해 다른 환자에게 직전 입력 예정값이 적용되지 않도록 한다.

## 검증 및 안전 범위

- 현재 v0.2.4 기준 **68개** Node 검사, **5개** Chromium 시나리오에 신규 예정·링크·분리 검사(18개 Node, 1개 Chromium)를 추가했다.
- 변경 로직은 생성·확인·수행·기록·선택적 링크·보관·그룹 조회에 한정한다.
- **기존 원본 파일**: `data/CATALOG.*`, `app/fixtures.js`, `app/activity-details.js`, `app/case-context.js`는 변경하지 않는다. 합성 후보 315, ACT 42, 환자 4, 시드 처방 16, 제품 18 IDs 동일.
- 무계획 주문으로 저장된 기존 객체, 제품 ID·표시명 스냅샷, 과거 수행·기록·감사 로그는 삭제/이동/자동 보정하지 않는다.
- `slotId`가 다른 처방을 가리키거나 보관된 일정의 개수/시각/상태가 불일치하면 **기존 저장값을 초기화하지 않고 오류를 알린다.**
- 사용자 사용성, 실제 nU 업무 흐름, 병원별 반복 주기·승인/보류/취소 권한, 실환자 시나리오, 실제 브라우저의 디스크 영속성 및 임상 안전성은 미검증이다.

## 다음 단계에 사용자와 합의할 결정

1. **예정 단위**: 특정 시각 슬롯(현 MVP) vs 근무조 시간창 vs 임상조건 기반 동적 예정 생성.
2. **예정 상태 변경**: 보류/취소/연기·재개 시 원본 보존, 변경자/시각/사유·감사 로그, 기존 수행이 연결된 슬롯을 변경할 때의 정책.
3. **반복 스케줄 지속성**: 현재는 처방 1건당 최대 24회 스냅샷. 무기한 정기 처방·일 단위 기간·시계 변경·수정 이력은 별도 설계.
4. **기록 현황 의미**: 단순 기록 연결 여부와 공식 기록 완료/서명/정정 상태를 혼동하지 않는 별도 워크플로 설계.
