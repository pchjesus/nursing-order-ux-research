# 간호처방 UI/UX — 합성 사용성 파일럿 준비 v0.1

> 2026-10-10 · 다음 개발 단계: **실제 현장 필요성 확인을 위한 평가 도구 준비**
> 실제 병원 nU와 무관한 독립형 가상 사례. **연구/임상 효용 검증 완료 문서가 아님**.

## 1. 이 단계에서 해결하려는 문제
PRN에서 확인한 것처럼 '없다고 생각한 기능이 이미 있는' 중복 개발을 피하기 위해, 간호처방 신규 기능 개발 전에 **구체적인 기존 업무와 사용자의 어려움**을 확인한다.

기존 승인 범위(A–C–C: 간호활동 중심 / 처방 전후 연계 / 혼합 탐색)는 유지하며, 이번 단계에서는 앱의 코드·화면·자료구조·기존 localStorage를 변경하지 않는다. **새로 만든 것은 분리된 합성 평가 사례와 관찰 프로토콜**이다.

## 2. 구현된 평가 도구
- `research/pilot-case-model.cjs`: 현재 코드의 ACT 42개를 실제로 로드하고 `NursingDomain`의 `search`, `groupPatientOrders`, `buildSchedule`, `scheduleOverview`, `summary`를 이용해 **임시 가상 사례를 메모리에서만 생성·검증**한다.
- `node research/pilot-case-model.cjs`: 연구자가 합성 검색 과제와 예상 개별 처방·예정·수행·기록 관계를 터미널에 JSON으로 조회. **데이터 생성/사용자 응답 저장 없음.**
- `tests/pilot-case-model.test.js`: 가상 ACT 코드·검색, 2개 독립 처방, 환자 분리, 예정/실제 사건/기록 건수, 조건부 미정, 손상된 참조 거부, 원본 불변을 점검한다. 기존 CI의 `tests/*.test.js`에 자동 포함된다.
- `research/OBSERVATION-TEMPLATE-v0.1.md`: 수기 관찰 기준, 비식별 코드, 기록하지 말아야 할 정보와 보고서 작성 형식.

**중요:** 파일럿의 B/C 사례는 원래 웹 UI의 브라우저 저장소에 주입하지 않는다. 현재 v0.2.5 화면에서 바로 해볼 수 있는 것은 **A 검색 과제** 및 기존 합성 환자 탐색이며, B/C는 **별도의 읽기 전용 모델 출력/종이 시나리오용**이다. B/C를 실 앱 화면에서 비교하려면 별도 격리된 평가 모드를 승인·구현해야 한다. 이 점을 숨긴 채 전체 대화형 테스트가 가능하다고 주장하지 않는다.

## 3. 과제별 수행 방법 / 해석 범위

| ID | 과제 | 현 파일럿에서 확인할 수 있는 정답·관찰 기준 | 반드시 구분할 내용 |
|---|---|---|---|
| A1 | '드레싱' 검색 결과 중 **정확한 표시명** '멸균 창상 드레싱 관리'를 찾아 코드 확인 | `SIM-ACT-0053`이라는 *텍스트/가상코드 식별*; `0052`·`0054`와 다름 | **임상적으로 어느 행위를 선택해야 한다는 정답이 아님** |
| A2 | 가상 코드 `SIM-ACT-0053` 단독 검색 | 정확히 1개 후보 | 실제 nU 처방 가능 코드를 뜻하지 않음 |
| B1 | 환자 A에 같은 코드로 된 **별도 가상 처방 2건**을 보여 주고 구분 | `PILOT-O-001` 조건부 / `PILOT-O-002` 3회 예정; ID는 2개 | 그룹 1개 ≠ 처방 1개, 임상 조건 동일성 아님 |
| C1 | 계획 3회, 모의 수행 1건, 연결 기록 0건 해석 | 건수는 각각 3·1·0; 계획 자동 누락 판정 금지 | 실제 미수행·기록 누락·완료 상태로 단정 불가 |
| C2 | 조건부 계획의 예정 횟수를 확인 | null = **미정** | 0회 수행 예정이 아님 |
| D1 | 환자 A/B의 개별 처방·수행 현황 구별 | 가상 환자 A 처방 2건, B 1건; A의 모의 수행 1건은 B의 이력이 아님 | 환자별 ID 분리 |
| E1 | 실제 간호처방 업무와 중복 기능 문의 | 기능 유무·사용 빈도·기존 우회방법 등을 질문 | 실제 현장 답변 전까지 결론 유보 |

A1/A2는 명칭·코드 탐색의 **정보검색 사용성**만 평가한다. B/C/D는 **구조화 기록 이해도** 평가이다. 실제 간호 술기 선택, 환자안전 효과, 병원 처방 권한을 시험한 결과가 아니다.

## 4. 추천 파일럿 절차 (향후 시행 시)
1. **Gate 0 / 기존 기능 확인:** 허용된 범위의 담당자 면담에서 간호처방의 실제 의미·권한·현재 시스템 검색/필터/그룹/이력 여부를 확인한다. 실제 병원 화면·내부 코드·환자정보의 무단 촬영/제공 금지.
2. 연구 목적과 가상 자료임을 안내하고 참가자를 **무작위 실명 없는 참가자 코드**로 구분한다. 실제 병원 직원식별번호·로그인·진료정보를 수집하지 않는다.
3. 기존 v0.2.5에서 A1/A2 수행. 관찰자는 수행 시간, 검색어 수정·되돌아가기, 목표 코드를 제대로 찾았는지, 기능 설명 요청 수를 기록한다.
4. B/C/D는 먼저 **이 문서와 CLI 출력의 정적 사례 카드**로 진행한다. 웹 UI 전체 사용성 과제로 분류하지 않는다.
5. 인터뷰: 혼동된 용어/건수의 뜻, 기존 EMR에서 이미 있는 기능과 비교해 필요한 것이 무엇인지 자유응답 확인.
6. 편향 점검: 같은 평가자가 연구 목적을 설명해 정답을 유도하지 않았는지, 순서 효과, 데모 환경 경험에 따른 차이를 확인한다.
7. 비교 UX 대안이 사용자 승인 후 준비된다면, **같은 합성 자료를 두 방식에 제공**하고 순서 편향을 고려해 시간/정확도/클릭 수를 비교한다.

## 5. 평가 지표 및 결과 보고 원칙
- **과제 정확성:** 가상 데이터 기준으로 제시한 목표 코드·건수를 정확히 식별했는지(0/1). **의학적 처방의 적절성 점수로 사용하지 않음**.
- **효율:** A1/A2 소요 시간(초), 검색 변경 횟수, 화면 이동 횟수, 도움 요청 횟수. 시작·종료 시점은 관찰자가 일관되게 기록.
- **혼동:** 개별 처방과 묶음·예정/수행/기록을 잘못 동일시한 횟수 및 짧은 설명.
- **수용성:** 이해하기 쉬운지, 불필요한 입력/확인이 늘어나는지 짧게 평가.
- **효과:** 사용자 수·숙련도·환경·표본 규모·대조 화면의 제약을 명시. **사전 자료/관찰 결과가 없는 상태에서 성공률, 개선율, 유의성이나 목표 수치를 만들어내지 않는다.**
- 문서화 구분: `자동 기능 검사` vs `사용자 과제 평가` vs `임상 효과 검증`. 이 세 가지는 별개다.

## 6. 현장 문제 검증을 위한 중립 질문
- 실제 '간호처방'에 포함되는 업무와 직접 등록할 권한은 무엇인가? 기존 전산 메뉴에 같은 기능이 이미 있는가?
- 같은 명칭이 반복되는 경우 어느 정보(부위, 목적, 수행방법, 빈도 등)로 구별하는가?
- 가장 번거로운 단계가 선택 전 검색, 등록, 수행 확인, 기록 중 무엇이며 **얼마나 자주** 나타나는가?
- 이미 제공되는 검색·즐겨찾기·코드 상세·최근 사용/그룹화 기능은 어떻게 쓰이는가?
- '규정 반영 지연'은 어떤 문서·업무 단계·최신화 절차의 문제인가? 실제 승인·보안 절차와 충돌하진 않는가?
- 신규 화면이 필요하다면 어떤 기능을 제거해 조작 단계를 줄일 수 있는가?

## 7. 다음 게이트 / 중지 조건
- **다음에 실행할 실제 작업:** 현장 질문을 검토받고 비식별 답변을 수집하여 `기존 기능 / 남은 불편 / 원인 / 빈도 / 영향 / 중복 가능성` 표로 정리.
- 근거가 없는 기능에는 *보류*; 현재 EMR에 동일 기능이 있고 충분하다면 *중단 또는 교육자료로 전환*.
- Gate 0을 통과하면 유사 후보 표시와 처방 후 상태 화면의 **작은 정보 배치 대안 1개**를 별도로 설계하고 승인받는다.
- 새 UX, ACT 코드, 병원 규칙, 저장/삭제, 인증·권한, PRN/MICU 병합을 이번 단계에서 도입하지 않는다.

## 8. 실행/검증 명령
```bash
node research/pilot-case-model.cjs
node tests/pilot-case-model.test.js
# 전체 회귀는 기존 GitHub Actions가 별도로 실행
```

이 도구의 출력은 **연구자 확인용 가상 예상 상태**이다. 직접 사용자 응답·참가자 기록을 수집하거나 저장하지 않는다.
