# 초기 정보 구조 설계안 — 미확정

## 1. 문제 정의
- 처방 전: 검색어와 코드의 불명확성, 유사 이름 구별, 카테고리 발견 가능성 및 오선택 위험
- 처방 후: 개별 처방의 상태, 수행 사건, 기록과 그 연결관계의 구분
- 데이터 기반: 실제 nU 데이터 없음. 합성 항목으로만 검증함

## 2. 개념 객체 (제안)

| 객체 | 역할 | 필수 검토 항목 |
|---|---|---|
| `catalog_item` | 합성 검색 항목; 실제 처방 정의와 별개 | 가상코드, 유형, 명칭, 동의어, 분류, 출처, 검증 상태 |
| `order_definition` | 처방 유형의 정의 | 코드, 버전, 실재 여부, 시행조건, 구별 속성 |
| `order_instance` | 해당 환자에게 등록된 개별 처방 | 별도 ID, 환자 컨텍스트, 상태, 등록 시각/권한/조건 |
| `execution_event` | 개별 수행 사건 | 별도 ID, 참조 처방, 수행 시각·수행자·결과·수정 이력 |
| `documentation_record` | 수행에 관한 기록 | 별도 ID, 작성·서명·정정 시각 및 기록자 |
| `execution_document_link` | 수행 사건과 기록 사이 관계 | 여러 수행과 여러 기록을 연결할 가능성 고려 |
| `material` | 물품/치료재료 정의 | 물품과 행위는 종류를 구별 |
| `activity_material_link` | 행위와 물품의 참고 관계 | 장비/소모품 사용이 처방 발생을 뜻하지 않음 |

**주의:** 개념 관계는 실제 데이터 스키마가 아니며, 어떤 행위가 의료진 처방을 필요로 하는지, 누가 수행 및 기록 가능한지 전혀 확정하지 않았음.

## 3. 처방 전 워크플로 후보
환자 식별 및 업무 맥락 확인 → 검색/분류 탐색 → 유사 후보 비교 → 상세조건 검토 → 초안 확인 → 권한·상태에 맞는 확정 처리

- `검색`은 이름, 승인된 동의어, 가상코드. 동의어 충돌 시 자동 선택 금지.
- `카테고리`는 탐색 보조 필터. 카테고리만 선택해야 검색 가능한 구조는 피함.
- `유사 처방`은 공식 명칭에 더해 부위·목적·대상·빈도 등 필요한 차이를 노출. 구별 항목은 처방별 검증 후 정의.
- `확정`은 검색/초안 추가와 분리. 이 단계의 세부 흐름은 추후 결정.

## 4. 처방 후 워크플로 후보
등록된 처방 조회 → 개별 처방 상세 → 예정/실제 수행 사건 조회 → 관련 기록 조회 → 상태/이력 비교

- 처방 수 = `order_instance` 수. 수행 수 = `execution_event` 수. 기록 수 = `documentation_record` 수. 서로 바꿔 표시 금지.
- 수행 수에서 기록 수를 차감하여 '기록 누락'이라고 단정하지 않음.
- 처방 취소·보류·연기와 미수행·미기록을 혼동하지 않음.
- UI에 요약 그룹을 표시해도 원본 주문/수행/기록 ID 및 순서/시간/정정 이력 보존.

## 5. 카테고리 UX 대안
A. 임상 목적 중심: 개념 이해는 쉬울 수 있으나 중복 카테고리 문제.
B. 업무 단계 중심: 작업순서에 적합하나 의미별 탐색이 어려울 수 있음.
C. 혼합형(잠정 추천): 상위 탭 `처방 찾기 / 현황 및 이력` + 내부 임상 카테고리.

아직 어느 안도 확정하지 않음. 현직 사용자 평가와 사용자 기획 결정 뒤 승인 예정.

## 6. 용어 표시 정책 제안
- 저장 원본 라벨과 코드의 신원 보존.
- 가독성 개선용 표시 라벨은 별도로 관리. 공식 원본인 것처럼 위장하지 않음.
- `SIM-*` 코드는 실제 운영용 코드가 아님을 UI에도 노출.
- 동의어는 검색 보조이며 개념 동등성을 뜻하지 않음.
